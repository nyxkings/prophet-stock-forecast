4.1 INTRODUCTION

This chapter describes the practical implementation of the Prophet-based portfolio
optimisation system developed in Python. The implementation translates the
methodological framework presented in Chapter Three into a deployable software
platform comprising a modular source-code library, automated data and forecasting
pipelines, mean-variance portfolio optimisation, persistent storage, interactive
visualisation, and supplementary analysis tools for backtesting and risk
assessment.

The system follows a layered architecture in which each component was developed
and unit-tested independently before integration through the central orchestration
function run_optimisation() in src/main.py. Version control was managed using Git
and GitHub (repository: nyxkings/prophet-stock-forecast), with scheduled
production execution configured via GitHub Actions. Local development used Cursor
as the integrated development environment, with dependency management handled by
Poetry (pyproject.toml).

A defining design decision in the production pipeline is the explicit separation
of forecasting inputs from risk estimation: Prophet-generated predicted returns
are passed directly to the optimiser as the expected return vector μ, while the
covariance matrix Σ is computed exclusively from historical daily returns. This
ensures that portfolio weights respond to forward-looking forecasts while risk
is measured from observed market co-movement, consistent with the methodology in
Chapter Three.

The portfolio under study consists of twelve publicly traded equities configured
in src/settings.py: AMD, MSFT, AAPL, TSLA, AMZN, NVDA, META, GOOG, TSM, JPM,
NFLX, and PLTR. Risk parameters were set to a balanced investor profile with a
risk aversion coefficient λ = 5, a minimum allocation of 5% per asset, and a
maximum allocation of 100%. Historical data defaults to the period from
2024-01-01 through the current date (END_DATE), providing approximately one to
two years of training data for Prophet and covariance estimation.

4.4 DATA EXTRACTION MODULE (extractor.py)

The data extraction module retrieves historical stock prices from Yahoo Finance
using the yfinance library. The public function extract_data() iterates over the
provided ticker list, downloads OHLCV data for each symbol over the configured
date range, and returns a dictionary mapping ticker symbols to processed
DataFrames.

For each ticker, the helper function _process_ticker_dataframe() performs four
transformations:

  (a) extraction of the closing price column and renaming to "Price";
  (b) calculation of daily simple returns using pandas pct_change();
  (c) removal of rows with missing values (first observation dropped); and
  (d) normalisation of the DatetimeIndex to Python date objects.

Error handling is implemented at the per-ticker level. If yfinance returns an
empty DataFrame (e.g. due to rate limiting or temporary API failure), the
ticker is logged as a warning and skipped rather than aborting the pipeline.
This defensive design allows partial portfolio runs when some symbols fail to
download, although the optimiser requires a non-empty intersection of aligned
tickers to proceed. Invalid symbols and network exceptions are caught in
_extract_single_ticker_data() and logged without terminating the full extraction
loop.

4.5 DATA PREPROCESSING MODULE (processor.py)

The preprocessing module aligns multiple ticker DataFrames to a common set of
trading dates. The function preprocess_data() computes the set intersection of
index dates across all successfully downloaded tickers and trims each DataFrame
to that shared calendar. This step is essential for covariance estimation: the
sample covariance matrix Σ requires synchronised return observations across
assets on identical trading days.

Two auxiliary functions support downstream consumers:

  - collect_recent_prices(): extracts the trailing 30 calendar days of closing
    prices per ticker. These series are serialised to Supabase as JSON arrays
    in the actual_prices_last_month column and used by the dashboard for price
    history sparklines and actual-vs-predicted comparison.

  - append_predictions(): appends a synthetic next-day row containing predicted
    price and return to each ticker's DataFrame. This function is retained for
    backward compatibility and unit tests but is not invoked by the production
    pipeline, which passes Prophet returns to the optimiser via the
    expected_returns parameter instead.

4.6 PROPHET FORECASTING MODULE (model.py)

The forecasting module implements the ProphetModel class, which fits an
independent Prophet model for each ticker in the portfolio. Fitting one model
per asset (rather than a multivariate model) keeps the implementation modular
and allows per-ticker failure isolation, at the cost of ignoring cross-asset
forecast dependencies.

4.6.1 Holiday and Seasonality Configuration

US stock exchange holidays are retrieved from the XNYS calendar via
pandas_market_calendars and passed to Prophet's holidays argument. This prevents
the model from treating exchange closures as missing observations and improves
weekly seasonality estimation. Prophet hyperparameters are loaded from
PROPHET_PARAMS in settings.py: yearly and weekly seasonality enabled, daily
seasonality disabled (appropriate for daily closing prices).

4.6.2 One-Step-Ahead Forecasting

The method predict_for_tickers() executes the following for each ticker:

  1. Read the last known closing price from the aligned historical DataFrame.
  2. Call predict_next(), which fits Prophet on the full price series and
     forecasts the next calendar day via model.predict().
  3. Compute the predicted simple return:
       r̂ᵢ = (ŷᵢ − Pᵢ,₀) / Pᵢ,₀
     where ŷᵢ is Prophet's point forecast and Pᵢ,₀ is the latest close.
  4. Accumulate results into two dictionaries: predictions (prices) and
     predicted_returns (returns).

The function returns both dictionaries as a tuple, enabling downstream modules
to use price levels for logging and return forecasts for optimisation.

4.7 PORTFOLIO OPTIMISATION MODULE (optimiser.py)

The optimisation module implements Markowitz mean-variance portfolio optimisation
using the Sequential Least Squares Programming (SLSQP) solver from SciPy's
optimize.minimize interface.

4.7.1 Expected Returns and Covariance Construction

The function calculate_mean_variance() constructs the inputs to the solver:

  - μ (expected returns): when the optional parameter expected_returns is
    supplied (as in production), μ is set directly from Prophet's
    predicted_returns dictionary with no averaging or blending with historical
    means. When expected_returns is None, μ falls back to the sample mean of
    historical returns (backward-compatible behaviour for tests).

  - Σ (covariance matrix): always computed from the last 252 trading days
    (approximately one year) of historical daily returns in the aligned
    portfolio_data. Forecast rows are never appended to this data in the
    production path, preventing contamination of risk estimates by predicted
    values.

4.7.2 Optimisation Problem

The objective function minimised is the negative of the mean-variance utility:

  f(w) = -(wᵀμ − λ/2 · wᵀΣw)

Subject to:
  - Equality constraint: Σwᵢ = 1 (fully invested portfolio)
  - Bound constraints: 0.05 ≤ wᵢ ≤ 1.0 per asset (MINIMUM_ALLOCATION)
  - No short selling (enforced by the lower bound)

The solver is initialised with equal weights and converges via SLSQP. The
optimal weight vector is returned as a dictionary mapping ticker symbol to
allocation proportion.

4.8 PIPELINE ORCHESTRATION (main.py)

The function run_optimisation() serves as the central orchestrator, executing
the complete end-to-end pipeline in a fixed sequence. Table 4.2 maps each step
to its implementing module and output.

Table 4.2: Production Pipeline Steps

| Step | Function / Class                    | Input              | Output                    |
|------|-------------------------------------|--------------------|---------------------------|
| 1    | extract_data()                      | tickers, dates     | raw price/return dict     |
| 2    | preprocess_data()                 | raw dict           | date-aligned dict         |
| 3    | ProphetModel.predict_for_tickers()  | aligned dict       | prices + predicted_returns|
| 4    | collect_recent_prices()             | aligned dict       | 30-day price history      |
| 5    | optimize_portfolio_mean_variance()  | aligned dict, μ    | optimal weights dict      |
| 6    | return result dict                  | all above          | structured JSON-like dict |

The critical integration between forecasting and optimisation occurs at Step 5:

  weights_dict = optimize_portfolio_mean_variance(
      portfolio_data,
      expected_returns=predicted_returns,
  )

Here portfolio_data contains only historical rows (Step 2 output), while
predicted_returns from Step 3 becomes μ. This wiring was verified by integration
tests (Section 4.14).

4.8.1 Command-Line Interface

The CLI entry point main() invokes run_optimisation() with PORTFOLIO_TICKERS
from settings.py and persists results via save_results_to_supabase(). When
invoked without arguments:

  poetry run python -m src.main

this executes the default optimise-and-save workflow unchanged.

Optional analysis commands are dispatched through src/analysis_cli.py when
provided as the first argument (backtest, risk, sector, analyze). These
commands extend the platform without altering the default production path.

4.9 DATABASE MODULE (database.py)

Results are persisted to a Supabase-managed PostgreSQL database. Supabase
credentials (SUPABASE_URL and SUPABASE_KEY) are read from environment
variables at runtime, ensuring no API keys are hardcoded in source files.
The same variables are injected into GitHub Actions via repository secrets for
scheduled production runs.

4.9.1 Schema and Row Structure

The function save_results_to_supabase() inserts one row per ticker per
optimisation run into the table stock_optimisation_store. Each row contains:

| Column                     | Type        | Description                              |
|----------------------------|-------------|------------------------------------------|
| id                         | UUID        | Unique row identifier (uuid4)            |
| created_at                 | TIMESTAMPTZ | Insertion timestamp                      |
| as_of_date                 | DATE        | Date the optimisation was run            |
| ticker                     | TEXT        | Stock symbol                             |
| predicted_price            | FLOAT       | Prophet next-day price forecast (ŷ)      |
| predicted_return           | FLOAT       | Computed expected simple return          |
| portfolio_weight           | FLOAT       | Optimal MPT allocation weight            |
| actual_prices_last_month   | JSONB       | Array of ~30 recent closing prices       |

The actual_prices_last_month field stores a JSON-encoded list of floats (e.g.
[315.20, 310.26, ...]) rather than a single scalar, enabling the dashboard to
render trailing price charts without re-downloading history from Yahoo Finance.

4.10 STREAMLIT DASHBOARD (streamlit_app.py and dashboard.py)

The presentation layer is implemented as an interactive Streamlit web
application. A thin root-level launcher (dashboard.py) imports and calls
main() from streamlit_app.py, providing a conventional entry point for
deployment and the Makefile target make dashboard.

4.10.1 Data Loading

The function load_supabase_predictions() queries stock_optimisation_store,
orders rows by as_of_date and created_at, deduplicates to one row per
(ticker, date), and returns a pandas DataFrame. If Supabase is unavailable or
empty, the dashboard falls back to generate_mock_portfolio_data() from
mock_data.py for demonstration purposes.

4.10.2 Dashboard Tabs

The interface is organised into five tabs:

  1. Overview — portfolio allocation pie chart, summary table of predicted
     prices, returns, and weights for the selected as-of date.
  2. Prediction Accuracy — per-ticker error metrics, heatmaps, and cumulative
     return charts comparing predicted vs actual prices over time.
  3. Advanced Analytics — prediction error heatmap and cross-ticker error
     correlation matrix.
  4. Performance Metrics — portfolio-level MAPE, RMSE, Sharpe ratio, volatility,
     and an on-demand "Compute advanced risk & sector metrics" panel that
     invokes RiskAnalyzer and SectorAnalyzer via portfolio_analysis.py.
  5. Efficient Frontier — interactive risk-return frontier exploration using
     the EfficientFrontier class.

The function calculate_portfolio_metrics() computes weight-adjusted portfolio
returns when portfolio_weight, actual_return, and predicted_return columns are
present, ensuring performance statistics reflect the optimised allocation rather
than equal-weighted averages.

4.11 ADVANCED ANALYSIS MODULES

Beyond the core production pipeline, four modules provide supplementary
analysis capabilities. These were integrated into the workflow via
src/portfolio_analysis.py (shared helpers) and src/analysis_cli.py (CLI
dispatch), without modifying the default optimise path.

4.11.1 Backtesting (backtesting.py)

The Backtester class implements walk-forward validation as described in the
methodology (Chapter Three, Section 3.8.2):

  1. Define a rolling training window (default: 252 trading days).
  2. For each test date (sampled every 5 business days), call run_optimisation()
     with history up to that date — inheriting the full Prophet → MPT pipeline.
  3. Compare predicted prices and returns against actual next-day observations.
  4. Compute per-date metrics: price MAPE, return MAPE, portfolio predicted and
     actual returns.
  5. Aggregate into a BacktestSummary with Sharpe ratio, volatility, max
     drawdown, and strategy outperformance.

CLI invocation: poetry run python -m src.main backtest [--start DATE] [--output FILE]

4.11.2 Risk Analytics (risk_analytics.py)

The RiskAnalyzer class computes portfolio and per-ticker risk metrics through
the RiskMetrics dataclass:

  - Value at Risk (VaR) at 95% and 99% confidence
  - Conditional Value at Risk (CVaR / Expected Shortfall)
  - Sharpe Ratio and Sortino Ratio (annualised)
  - Maximum Drawdown and Calmar Ratio
  - Volatility, skewness, kurtosis
  - Portfolio concentration (Herfindahl index, effective number of assets)

CLI invocation: poetry run python -m src.main risk

4.11.3 Sector Analysis (sector_analysis.py)

The SectorAnalyzer class maps tickers to GICS-style sectors via TICKER_SECTOR_MAP,
computes sector weights, Herfindahl-Hirschman concentration, and per-sector
volatility and expected-return contributions. This supports diversification
analysis beyond individual-asset weights.

CLI invocation: poetry run python -m src.main sector

4.11.4 Portfolio Analysis Bridge (portfolio_analysis.py)

This module provides shared functions used by both the CLI and the Streamlit
dashboard: loading aligned returns data, computing weighted portfolio return
series, formatting backtest summaries, and serialising sector analysis results
for tabular display.

Makefile targets: make backtest, make risk, make sector, make analyze

4.14 DEPLOYMENT

The completed system is deployed with the following automation and infrastructure
components:

4.14.1 Scheduled Optimisation (GitHub Actions)

The workflow .github/workflows/daily-optimisation.yml runs at 09:00 UTC daily
(and supports manual workflow_dispatch). It checks out the repository, installs
dependencies via Poetry, sets SUPABASE_URL and SUPABASE_KEY from GitHub secrets,
and executes poetry run python -m src.main. This provides unattended daily
forecasting, optimisation, and database persistence.

4.14.2 VPS Hosting

A deployment script (scripts/deploy.sh) pulls the latest code on a Hostinger VPS,
installs dependencies if pyproject.toml changed, and restarts the Streamlit
systemd service. The investor dashboard is accessible via the project domain;
the admin dashboard (streamlit_admin.py) provides operational monitoring.

4.14.3 Environment Configuration

Production and local environments require:

  SUPABASE_URL   — Supabase project REST endpoint
  SUPABASE_KEY   — Supabase anon/public API key

These are never committed to the repository. Local runs use export or a sourced
.env file; CI uses GitHub Actions secrets.

realising the methodological design of Chapter Three in working software.
Supplementary analysis commands (backtest, risk, sector) and the Streamlit
dashboard provide end-to-end usability for investment analysis, risk reporting,
and historical performance tracking.
